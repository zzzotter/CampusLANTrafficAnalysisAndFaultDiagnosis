## 2. 支持 / 不支持清单（被问就说这张表）

| 支持 | 不支持（已在文档注明） |
| --- | --- |
| Ethernet 帧、IPv4 | VLAN 双标签帧 |
| IPv6 基础字段（地址 + 下一头部） | IP 分片重组 |
| TCP：端口、6 个标志位、seq/ack/window、载荷长度 | TCP 选项、TLS/HTTP 应用层内容 |
| UDP：端口、长度 | ICMP 类型/代码细分 |
| DNS：域名、qtype、响应码、请求/响应方向、应答数 | 非以太网链路（如 `tcpdump -i any` 的 Linux cooked capture） |
| PCAP 与 PCAPNG 两种文件格式 | 加密流量内容 |

## 3. 已知限制（主动说，比被问出来好）

1. 抓包被 `snaplen` 截断时上层字段可能缺失，这类记录标 `partial`，基础字段仍可用。
2. 抓包点位置影响结果：只抓到单向流量时，DNS 只能看到请求看不到响应，B 的"无响应"判定要结合这一点解释。
3. 这是课程原型，不做实时抓包、不做长期存储；解析速度约 7000 包/秒，超大文件建议先截取或改用 `iter_packets()` 流式处理。

## 4. 可能被问到的问题

**Q：为什么 12 个包只解析 11 个，是不是漏包了？**
A：漏的那 1 个是 ARP。ARP 没有 IP 层，我们不做二层的 MAC 解析，所以按约定跳过并计数，覆盖率说明里能看到"跳过 1"。

**Q：覆盖率是成功率吗？**
A：是（成功 + 部分解析）/ 总包数。部分解析指报文本身坏了但 IP/端口/长度仍能取到，这种包仍然对统计有用，所以算进 packets。

**Q：坏文件会不会让整个程序退出？**
A：不会。三层兜底：文件级（不存在/空/损坏 → 中文提示）、单包级（异常只跳过该包）、文件中途损坏（已解析的部分照常返回）。我们有 6 类坏输入的压测记录。

**Q：为什么字段比队长文档多？**
A：核心 7 个一字未改；多出来的是纯追加的扩展字段。原因很直接：7 个字段里没有 DNS 响应码和 TCP 标志位，B 的"DNS 失败/连接失败"两条规则就写不出来。扩展字段可以不看，要用的时候才取。

**Q：TCP 重传你怎么判的？**
A：解析器只提供"同四元组 + 同 seq"的原始字段，重传判定在 B 的规则里做，而且我们的报告只称"异常线索"，因为抓包点和丢包会干扰判断。

**Q：支持 IPv6 吗？**
A：基础字段支持（地址、下一头部、TCP/UDP 端口），样例 `normal.pcap` 里就有一个 IPv6 包，统计里能看到 IPv4 10 条 / IPv6 1 条。

**Q：能处理多大的文件？**
A：实测 1 万包 / 1 MB 用时约 1.4 秒；再大建议用 `iter_packets()` 流式读，避免一次性进内存。
